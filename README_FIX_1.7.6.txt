۱) باگِ اصلی و مرگ‌آور  —  app/database/engine.py
--------------------------------------------------------------
علت: در تابع init_models() پَچ‌های جدیدِ اسکیمای «v1.7.6.2» اشتباهی
بینِ بدنهٔ «if _is_sqlite:» و «else:» گذاشته شده بودند.

در پایتون، try/except می‌تواند بندِ else هم داشته باشد؛ بنابراین آن
«else:» دیگر به «if _is_sqlite» وصل نبود و به «try» بالای خودش
چسبیده بود. نتیجه:

  * روی SQLite بلوکِ try موفق می‌شد، پس بلوکِ else اجرا می‌شد.
  * بلوکِ else فقط برای PostgreSQL است و از این دستور استفاده می‌کند:
        ALTER TABLE ... ADD COLUMN IF NOT EXISTS ...
  * SQLite این گرامر را ندارد =>
        sqlite3.OperationalError: near "EXISTS": syntax error
  * init_models() خطا می‌داد -> ensure_started() خطا می‌داد ->
    passenger_wsgi هر آپدیت را رد می‌کرد -> بات کاملاً قطع.

در لاگ: ۱۸۴ بار همین خطا + ۲۳۷ بار
"passenger_wsgi failed to process update".

اصلاح: پَچ‌های جدید به داخلِ شاخهٔ درستِ «if _is_sqlite:» منتقل شدند
تا «else:» دوباره به «if _is_sqlite» وصل شود.

علامت:
  در منوی «کارخونه» (و همچنین «برند») وقتی تولید لغو می‌شد، چند برابر
  هزینه‌ی مواد اولیه به کاربر برگردانده می‌شد.

علت ریشه‌ای:
  در داده‌ی محصولات، کلید raw_cost هزینه‌ی مواد برای یک «دسته» (batch)
  است، نه یک واحد. هزینه‌ی هر واحد = raw_cost / batch.

  هنگام شروع تولید، کد به‌درستی از تابع raw_cost_for_units() استفاده
  می‌کرد (که بر batch تقسیم می‌کند). اما کد لغو تولید، raw_cost را
  مستقیماً قیمت هر واحد فرض می‌کرد:

      refund = (units * raw_cost) // 2        <-- غلط

  نتیجه:  بازپرداخت / پرداختی  =  batch / 2
  یعنی برای محصولات با batch=10 مثل «پارچه» و «مشروب» و «پوشاک آماده»
  کاربر ۵ برابر مبلغ پرداختی را پس می‌گرفت => چاپ بی‌نهایت پول.

نمونه‌ی عددی (۱۰۰ واحد پارچه، batch=10):
  پرداختی واقعی .......  40,000
  بازپرداخت قبلی ...... 200,000   (۵ برابر - سود خالص ۱۶۰,۰۰۰)
  بازپرداخت جدید ......  20,000   (دقیقاً ۵۰٪)

اصلاح:
  در هر ۴ نقطه، بازپرداخت از همان تابعی محاسبه می‌شود که پول را کم
  کرده بود، سپس نصف می‌شود:

      paid   = raw_cost_for_units(key, units, speed_level)
      refund = max(0, paid // 2)

[7-1] باگ اصلی: دکمه «بیمارستان / تعمیر» روی لوپ گیر می‌کرد

فایل: app/services/battle_live.py  (تابع hospital_heal)

کد معیوب:
    player = (await session.execute(select(Player).where(...))).scalar_one_or_none()
    if player is None:
        from sqlalchemy import select          <-- ریشه باگ
        player = (await session.execute(select(Player).where(...))).scalar_one_or_none()

چرا خراب بود:
  در پایتون هر «import» داخل بدنه یک تابع، آن نام را برای کل آن تابع «محلی»
  (local) می‌کند - نه فقط از خط import به بعد. پس نام select در تمام تابع
  محلی بود و خط اول (که پیش از آن import اجرا می‌شد) با خطای زیر می‌ترکید:

      UnboundLocalError: cannot access local variable 'select'
      where it is not associated with a value

  این استثنا از hospital_heal بالا می‌رفت و بیرون می‌زد، پس اجرای هندلر هرگز
  به «await callback.answer()» نمی‌رسید. تلگرام تا وقتی به یک callback_query
  پاسخ نگیرد، چرخانِ «در حال بارگذاری» را روی همان دکمه نگه می‌دارد - یعنی
  دقیقاً همان چیزی که کاربر «گیر کردن روی لوپ» دیده بود. زدن دوباره دکمه هم
  همین چرخه را تکرار می‌کرد.

  نکته: select از قبل در سطح ماژول (خط ۱۸ همان فایل) import شده بود، پس آن
  import داخل تابع از اول هم بی‌فایده بود.

اصلاح: import محلی و پرس‌وجوی تکراری حذف شد؛ همان select سطح ماژول به کار
       می‌رود.

===============================================================================
۱۷) بخشِ تازه: استخدامِ شهردار و پیامِ مردم (v1.7.6.5)
===============================================================================

پیش از این، maybe_mayor_demands() بی‌قیدوشرط برای همهٔ شهرها پیام می‌فرستاد و
متنِ آن فقط سه جملهٔ ثابت بود. مفهومِ «شهردار» به عنوان کسی که استخدام
می‌شود وجود نداشت. حالا:

app/data/city_mayor.py (تازه) — سه رده:
  • کارمندِ شهرداری  — ۴۰M استخدام، ۸M حقوق، ۱ گزارش/سال، +۲٪ رضایت
  • مدیرِ شهری         — ۱۵۰M استخدام، ۳۰M حقوق، ۲ گزارش/سال، +۵٪ رضایت
  • شهردارِ کارکشته   — ۵۰۰M استخدام، ۹۰M حقوق، ۴ گزارش/سال، +۹٪ رضایت

عمقِ گزارش به رده بستگی دارد: ۱ خلاصه، ۲ فهرستِ نیازهایِ برآورده‌نشده،
۳ به‌علاوهٔ دلیلِ دقیقِ توقفِ رشدِ جمعیت (از همان growth_blocker بندِ ۱۶).

ستون‌هایِ تازهٔ mafia_cities:
  mayor_key, mayor_hired_at, last_mayor_msg_at, mayor_paid_at
مهاجرتِ صریح در هر دو شاخهٔ init_models اضافه شد (SQLite با PRAGMA table_info و
بدونِ IF NOT EXISTS؛ PostgreSQL با ADD COLUMN IF NOT EXISTS در try/except).
یادآوری: create_all هرگز ستون به جدولِ موجود اضافه نمی‌کند.

دکمهٔ «🏛️ شهرداری و پیامِ مردم» در داشبوردِ شهر اضافه شد و adjust به
(2, 2, 2, 1, 1, 1, 1) گسترش یافت تا دقیقاً ۱۰ دکمهٔ زمانِ اجرا را پوشش دهد.

هندلرها: city:mayor:hire:<key> و city:mayor:fire و city:mayor
ترتیبِ ثبت مهم است — دو تای اول باید قبل از هندلرِ عمومی بیایند، وگرنه
فیلترِ startswith("city:mayor") هر دو را می‌بلعد.

حقوق: در هر مرزِ سالِ بازی یک بار از موجودی کم می‌شود. اگر پول نباشد،
شهردار خودبه‌خود می‌رود (مقدارِ بازگشتی -1 در _charge_mayor_salary).

تیکر حالا فقط به شهرهایی پیام می‌دهد که شهردار استخدام کرده‌اند، فاصلهٔ
گزارش‌ها را از ردهٔ شهردار می‌گیرد، و زمان را در ستونِ last_mayor_msg_at
ذخیره می‌کند (پیش‌تر از کلیدِ تنظیماتِ ادمین mayor_msg_<uid> استفاده می‌شد).

درسِ تست‌نویسی از این دور
-------------------------------------------------------------------------------
چهار «خطا»ی اولیهٔ verify_city_mayor.py همه ایرادِ خودِ تست بودند، نه کد:
  • الگوی "mayor_msg_" زیررشتهٔ "last_mayor_msg_at" است.
  • رشتهٔ startswith("city:mayor") در کامنتِ خودِ کد هم پیدا می‌شد — باید روی
    دکوراتور لنگر انداخت.
  • شمارشِ دکمه باید در if/else بیشترین شاخه را بردارد، نه جمعِ دو شاخه.
  • engine.py سه جای مختلف if _is_sqlite دارد؛ دومی پنج PRAGMA دارد (WAL) و
    تست اشتباهی آن را می‌گرفت. باید جست‌وجو را به init_models() محدود کرد و
    وجودِ شاخهٔ else را الزامی کرد.

وقتی تستی رد می‌شود، اول با یک پروبِ مستقل معلوم کن کد خراب است یا تست.
